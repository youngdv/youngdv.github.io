VDOT MRP · Operations Hub

One place to see, review and act on field inspections

I designed the web counterpart to the VDOT MRP field app. It takes inspection data collected on the highway and shows it on a map and in tables, so district staff can track asset conditions, manage access across districts, and act without re-entering data by hand.

01
The problem

Field data with nowhere to go

Inspectors were collecting data on the mobile app, but office staff had no central place to view, filter or act on it. The platform had to serve three roles with very different permissions, all in one interface.

As Lead UX Designer, I owned the full design of the web platform and contributed to front-end development, refining the information hierarchy through stakeholder feedback at sprint reviews.

Regular users: their own projectsAdmins: one districtSuper Admins: every district and user
02
Design decisions

One platform, built around how each role works

Two views of the same data

A map for geographic context, matching how inspectors already think about their walk-arounds, and a filterable table for scanning, sorting and exporting. Admins live in the table.

Match the mental model

Role-gated, not three apps

One interface with views gated by role: users see their projects, Admins their district, Super Admins everything, including user approvals.

Consistency

A clear place to start

Occasional users didn't know where to go first. A menu anchored to the profile tab gives a quick entry point to projects and role views without cluttering the main navigation.

Reduce "where do I start?"
03
Design to code

From prototype to production

Working in the React codebase, I built the dashboard's front end from my own Figma components: the status indicators, the map detail popover, the filterable data table, the Map/Tabular toggle and the responsive Display Control Panel. I managed my revisions with Git and ramped up on React by pairing with the team's software engineer, AI-assisted development and independent learning.

04
Pre-launch iteration

Redesigning account approvals

Super Admins approve every new user, so the request queue is where access decisions happen. The admin platform hasn't launched yet, so before launch I reviewed my first version of these screens against usability heuristics and WCAG 2.1 AA and redesigned the approval flow.

Show what's being granted

A Requested role column and summary cards for the requests that carry the most access: Admin roles and statewide jurisdiction.

Recognition rather than recall

Fewer steps to the right request

A three-step filter builder became one bar with search plus Jurisdiction and Role filters. Bulk Approve and Deny clear a queue at once.

Flexibility and efficiency

Neutral decisions

Approve and Deny share one neutral style and size on every row, so nothing nudges an admin toward granting access.

Error prevention

Accounts at a glance

Status tabs with live counts, and a labeled "More" menu instead of an unlabeled icon, with a clear name for screen readers.

Visibility of status · WCAG labels
05
Design system

One system, two platforms

The dashboard and the field app share one design system: Inter type, a navy and orange palette, and the same status logic. Tokens are sized per platform: 56px controls for gloved hands in the field, 35px so managers can scan dense tables at a desk. Every text color passes WCAG 2.1 AA, and status always carries a word.

Color

Navy and orange carry the brand. Every text pairing passes WCAG 2.1 AA (4.5:1), most pass 7:1, for reading in direct sun.
